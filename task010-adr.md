## Часть 10.1 — Анализ критически важных данных

### Части данных интернет-магазина, критически важные с точки зрения целостности и скорости обработки:

1. Заказы (orders):
* Целостность: ошибки в данных о заказах могут привести к потере доходов и недовольству клиентов. Например, неправильная обработка статуса заказа может вызвать задержки в доставке или ошибки в выставлении счетов.
* Скорость обработки: быстрая обработка заказов необходима для обеспечения своевременной доставки и высокого уровня обслуживания клиентов.

2. Товары (products):
* Целостность: данные о наличии, ценах и характеристиках товаров должны быть актуальными. Продажа недоступного товара или предложение устаревшей цены могут привести к потере доверия клиентов.
* Скорость обработки: быстрое получение данных о товарах необходимо для обеспечения удобного поиска и просмотра товаров на сайте.

3. Корзины (carts):
* Целостность: данные о содержимом корзин должны быть актуальными, чтобы избежать ошибок при оформлении заказа.
* Скорость обработки: быстрая загрузка информации о корзине позволяет пользователям оперативно управлять своими покупками.

4. Пользовательские сессии (user sessions):
* Целостность: данные о текущих сессиях пользователей важны для обеспечения безопасности и удобства использования сайта (например, сохранение состояния авторизации, предпочтений пользователя).
* Скорость обработки: быстрая обработка сессий необходима для минимизации времени отклика сайта и обеспечения плавного пользовательского опыта.

5. История заказов (order history):
* Целостность: корректность данных об истории заказов важна для предоставления клиентам возможности отслеживать свои прошлые покупки и для анализа поведения пользователей.
* Скорость обработки: быстрый доступ к истории заказов позволяет пользователям быстро находить информацию о своих предыдущих покупках, что повышает уровень удовлетворённости.


### Для каких данных применение Cassandra имеет смысл:

1. Заказы (orders):
* Масштабируемость: Cassandra позволяет легко масштабировать систему для обработки большого количества заказов в периоды пиковой нагрузки (например, во время «чёрной пятницы»).
* Скорость записи/чтения: высокая скорость обработки данных важна для быстрой регистрации и обработки заказов.
* Отказоустойчивость: leaderless-репликация обеспечивает высокую доступность данных, минимизируя риск потери информации.

2. Товары (products):
* Масштабируемость: при большом объёме данных о товарах Cassandra позволит эффективно распределять данные между узлами.
* Геораспределённость: если интернет-магазин работает в нескольких регионах, Cassandra может обеспечить быстрое чтение данных о товарах из ближайшего дата-центра.
* Скорость чтения: быстрое получение данных о товарах важно для обеспечения хорошего пользовательского опыта.

3. Корзины (carts):
* Масштабируемость: в периоды пиковой нагрузки Cassandra сможет эффективно обрабатывать большое количество запросов о состоянии корзин.
* Скорость обработки: быстрая работа с данными о корзинах позволит пользователям оперативно управлять своими покупками.
* Отказоустойчивость: высокая доступность данных гарантирует, что информация о корзинах будет доступна даже при сбоях отдельных узлов.

4. Пользовательские сессии (user sessions):
* Скорость обработки: Cassandra обеспечивает быструю запись и чтение данных, что важно для обработки сессий пользователей.
* Масштабируемость: возможность горизонтального масштабирования позволяет справляться с ростом числа пользователей.
* Отказоустойчивость: распределённая природа Cassandra гарантирует высокую доступность данных о сессиях.

5. История заказов (order history):
* Масштабируемость: большое количество данных об истории заказов требует системы, способной эффективно масштабироваться.
* Скорость чтения: пользователи ожидают быстрого доступа к своей истории заказов, и Cassandra может обеспечить необходимую производительность.
* Распределённость данных: если данные распределены по разным регионам, Cassandra обеспечит быстрый доступ к ним.

## Часть 10.2 — Концептуальная модель данных и ключи

### Концептуальная модель для критически важных сущностей в Cassandra
1. Заказы (orders)
* Partition key: order_id.
* Кластерный ключ: order_date, customer_id.

2. Товары (products)
* Partition key: category_id.
* Кластерный ключ: product_id, price.

3. Корзины (carts)
* Partition key: user_id.
* Кластерный ключ: cart_id, item_count.

4. Пользовательские сессии (user sessions)
* Partition key: session_id.
* Кластерный ключ: user_id, session_start_time.

5. История заказов (order history)
* Partition key: customer_id.
* Кластерный ключ: order_id, order_date.


#### Цель схемы: обеспечить равномерное распределение данных и эффективный доступ в условиях экстремальной нагрузки, минимизировать влияние решардинга при изменении топологии кластера.


## Часть 10.3 — Стратегии обеспечения целостности

### Стратегии обеспечения целостности данных в Cassandra

#### 1. Hinted Handoff:
* Суть: временно сохраняет данные на других узлах, если целевой узел недоступен, и пытается отправить их после восстановления работы узла.
* Подходит для сущностей:
* * Заказы (orders): важна сохранность данных о заказах, так как ошибки могут привести к потере доходов и недовольству клиентов.
* * Корзины (carts): необходимо гарантировать актуальность данных о корзинах, чтобы избежать ошибок при оформлении заказа.
* Компромиссы: увеличивает нагрузку на сеть и требует дополнительных ресурсов для хранения временных данных, но обеспечивает более высокий уровень гарантии целостности данных. Latency может незначительно увеличиться, однако это оправдано для критически важных данных.

### 2. Read Repair:
* Суть: при чтении данных система обнаруживает расхождения между копиями на разных узлах и автоматически обновляет их.
* Подходит для сущностей:
* * Товары (products): важно поддерживать актуальность данных о товарах (цена, наличие), чтобы избежать продажи недоступного товара или предложения устаревшей цены.
* * История заказов (order history): корректность данных об истории заказов важна для предоставления клиентам возможности отслеживать свои прошлые покупки.
* Компромиссы: может немного увеличить время чтения, так как система должна проверить и обновить данные. Однако это обеспечивает более высокий уровень согласованности данных без значительного влияния на производительность в обычных условиях.

### 3. Anti-Entropy Repair:
* Суть: периодический процесс, который сканирует и синхронизирует данные между узлами, устраняя расхождения.
* Подходит для сущностей:
* * Пользовательские сессии (user sessions): хотя данные о сессиях важны, их потеря не так критична, как потеря данных о заказах или товарах. Периодическая синхронизация будет достаточной для поддержания целостности данных.
* Компромиссы: требует значительных ресурсов и может временно увеличить нагрузку на систему. Однако обеспечивает высокий уровень согласованности в долгосрочной перспективе и подходит для менее критичных сущностей, где допустимо периодическое обновление данных.


### Обоснование выбора

Для сущностей с высокой критичностью (orders, carts) предпочтительны стратегии, обеспечивающие максимальную сохранность и актуальность данных (Hinted Handoff, Read Repair), несмотря на небольшое увеличение latency.
Для менее критичных сущностей (user sessions) можно использовать Anti-Entropy Repair, так как периодическая синхронизация будет достаточной, а ресурсы системы будут использоваться более эффективно.
