# ADR-003: Настройка чтения с реплик и консистентность

**Статус:** Принято  
**Дата:** 2025-07-29  
**Участники:** Архитектурный комитет «Мобильный мир»  

---

### Таблица операций чтения для коллекций products, orders и carts

| Коллекция | Операция чтения                                                                                        | Реплика для чтения | Обоснование                                                                                                                                                                                                                                              |
| --------- | ------------------------------------------------------------------------------------------------------ | ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| products  | Поиск товаров по категории (`db.products.find({ category: "Электроника" })`)                           | secondary          | Требования к консистентности данных некритичны — небольшое устаревание данных о категориях и товарах не приведёт к серьёзным последствиям для бизнеса. Частота обновлений товарных позиций не настолько высока, чтобы требовать строгой консистентности. |
| products  | Поиск конкретного товара по ID (`db.products.find({ _id: "prod001" })`)                                | primary            | Необходимо обеспечить актуальную информацию о наличии и цене товара, чтобы избежать продажи недоступного товара или предложения устаревшей цены.                                                                                                         |
| orders    | Поиск истории заказов пользователя (`db.orders.find({ customer_id: "cust001" })`)                      | secondary          | Для просмотра истории заказов допустимо небольшое отставание данных — пользователь не будет критически зависеть от мгновенной актуальности этой информации.                                                                                              |
| orders    | Проверка текущего статуса заказа (`db.orders.find({ _id: "ord001" })`)                                 | primary            | Актуальность статуса заказа критически важна — пользователь должен видеть текущий статус своего заказа, чтобы понимать, на каком этапе находится его обработка.                                                                                          |
| carts     | Получение текущей корзины пользователя (`db.carts.find({ user_id: "cust001", status: "active" })`)     | secondary          | Для отображения содержимого корзины допустимо небольшое отставание данных, так как изменения в корзине обычно не происходят с очень высокой частотой.                                                                                                    |
| carts     | Операции, связанные с изменением статуса корзины (например, проверка статуса перед оформлением заказа) | primary            | Необходимо гарантировать актуальность статуса корзины, чтобы избежать ошибок при оформлении заказа или других операциях.                                                                                                                                 |

### Допустимая задержка репликации

Для операций на secondary репликах допустимая задержка репликации зависит от специфики операций:
- для операций с коллекцией `products` (поиск по категориям) — задержка до нескольких минут может быть допустима;
- для операций с коллекцией `orders` (поиск истории заказов) — задержка до нескольких секунд может быть приемлема, но для проверки текущего статуса заказа задержка должна быть минимальной (несколько секунд или меньше);
- для операций с коллекцией `carts` (получение текущей корзины) — задержка до нескольких секунд обычно допустима, но для операций, связанных с изменением статуса корзины, задержка должна быть минимальной.

### Обоснование выбора

Выбор между primary и secondary репликами определяется следующими факторами:
- **Требования к консистентности данных:** для операций, где критична актуальность данных (например, проверка статуса заказа или корзины), необходимо использовать primary реплику. Для менее критичных операций (например, поиск товаров по категориям или история заказов) можно использовать secondary реплику.
- **Частота обновлений:** коллекции, которые обновляются с высокой частотой (например, статусы заказов или содержимое корзин), требуют более строгой консистентности, поэтому для них предпочтительнее primary реплика.
- **Бизнес-логика:** ошибки, связанные с устаревшими данными, могут привести к потере доверия клиентов (например, продажа недоступного товара или отображение устаревшего статуса заказа). Поэтому для таких операций важно минимизировать задержку репликации.
